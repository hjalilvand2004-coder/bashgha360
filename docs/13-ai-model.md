# ۱۳ — مستند مدل هوشمند (REC) — طبق بخش ۱۲ سند کارفرما

## ۱. نسخهٔ فعلی: توصیه‌گر قاعده‌محور (rules-1.0)

**ورودی‌های مجاز (فقط همین‌ها):** هدف منتخب، پیشرفت معتبر (تجمعی)، علایق/هدف اعلامی، شرایط و ظرفیت، سابقهٔ درخواست فعال.
**ورودی‌های ممنوع:** دادهٔ مالی، سلامت، هر برچسب «ضعیف/پرریسک».

**گام‌ها (REC-01):**
1. بررسی رضایت شخصی‌سازی → `basis=consent_personal` یا `generic` (بدون رضایت هم کار می‌کند — TST-11)
2. فهرست پاداش‌های مجاز (فعال، غیرضروری-قابل‌خرید)
3. فیلتر ظرفیت/شرایط رشته
4. تطبیق `goal_tags` با هدف اعلامی (+۰.۵)، ظرفیت آزاد (+۰.۲)، بدون هزینه (+۰.۱)
5. تنوع: حداکثر ۲ آیتم از هر نوع، خروجی ≤ ۶
6. **دلیل واقعی محاسبه‌شده** برای هر آیتم (مثلاً «تناسب با هدف "تقویت مهارت وب"») — متن ساختگی تولید نمی‌شود (REC-07)
7. بازخورد like/not_now/dismiss ذخیره می‌شود (REC-07/مرحلهٔ ۲ برای یادگیری)

## ۲. توسعهٔ ML (مرحلهٔ دوم/سوم — Backlog BL-02)
- Provider Interface از الان قابل تعویض است؛ مدل فعلی = پیاده‌سازی پیش‌فرض.
- الزامات پیش از فعال‌سازی: Dataset Version و Model Version ثبت‌شده، تفکیک Train/Validation/Test بدون Leakage، مقایسه با خط پایهٔ قاعده‌محور، ارزیابی اثربخشی/انصاف/Cold Start، Kill Switch برگشت به rules-1.0، پایش Drift.
- LLM در هسته نیست و هیچ حق تغییر امتیاز/شرایط/حکم ندارد (REC-06).

## ۳. کشف ناهنجاری (INT)
- فعلی: کنترل‌های قطعی + Rule-based Checks با عنوان صریح (`BURST_VOLUME_1H`, `REPEAT_ACTIVITY_24H`, …) که فقط پرونده می‌سازند.
- آینده (مرحلهٔ سوم): مدل ناهنجاری پس از کفایت داده و برچسب پرونده‌ها؛ همیشه advisory، هرگز حکم.
